# 0012. Протокол синхронизации и серверная схема

Статус: принято · 2026-11-15 · уточняет [ADR-0009](0009-backend-sync-health-data.md) (раздел «Синхронизация», «Модель»
и п. 3–6, 9, 10; «Следующие шаги», п. 3), [ADR-0010](0010-local-schema-for-sync.md) (правила отправки и получения) и
[ADR-0011](0011-natural-ids-migration.md) (п. 9, tombstone на элементе приёма пищи); контракт ядра #277

## Контекст

ADR-0009 решил, **что** делает синхронизация: очередь уходит на сервер пачками, сервер присваивает `rev` и подрезает
время из будущего, устройство получает изменения по курсору, конфликт решает last-writer-wins, приём пищи сливается
по элементам. ADR-0010 и ADR-0011 подготовили локальную базу. Открытым оставалось, **как** это выглядит в коде и в
Postgres:

- в каком виде запись едет по сети и лежит на сервере, если её поля знает только клиент и они добавляются с каждой
  версией приложения;
- кто применяет правило конфликта — сервер, клиент или оба — и что делать с push, который приходит раньше pull
  (движок сначала отправляет, потом получает): более поздняя версия приёма пищи перезаписала бы на сервере чужие
  элементы, которых устройство ещё не видело;
- как курсор `rev` не пропускает изменения при одновременных отправках;
- что получает устройство, чья правка проиграла, если его часы отстают и pull эту версию уже не принесёт;
- как именно устроены «устройство после 90 дней офлайн» и «заменить данные в облаке».

## Решение

1. **Одна форма версии строки везде** — `SyncChange` (`core/sync/protocol.ts`):
   `{ table, key, updatedAt, updatedBy, deletedAt?, data? }`. `table` — имя таблицы приложения, `key` — её первичный
   ключ (`id`, у `settings` — `key`), `data` — строка как на устройстве **без** ключа и служебных полей
   (`updatedAt`, `updatedBy`, `deletedAt`). У tombstone `data` нет: удалённое пользователем не отправляется
   (ADR-0010, п. 1), сервер стирает содержимое tombstone, даже если клиент его прислал.
2. **На сервере — таблица на каждую синхронизируемую таблицу приложения, а запись лежит в `data jsonb`.** Колонки —
   то, что нужно синхронизации и доступу: `user_id`, `id`, `rev`, `updated_at`, `updated_by`, `deleted_at`,
   `received_at`; времена — миллисекунды эпохи, как на устройстве. Таблицы (`tasks`, `sleep_logs`, …) — разделы
   общей `sync_rows` по имени таблицы приложения, поэтому `sync_push` и `changes_since` — обычный статический SQL по
   одной таблице, без динамического SQL в функции с правами владельца.
   Это уточнение «Модели» ADR-0009 («та же форма записи плюс `user_id`, `rev`, …»): форма записи хранится целиком,
   но не колонками. Колонки на каждое поле отвергнуты: схема клиента только растёт (ADR-0009, п. 8), и поле, которого
   сервер ещё не знает, колонка молча отбросила бы — оно пропало бы на других устройствах, а с эхом отправки и у
   автора; каждое новое необязательное поле требовало бы миграции сервера **до** выхода приложения. Аналитика и модели
   по ADR-0009 читают не сырые таблицы, а витрины — их строит SQL по `data`.
3. **Единственный путь записи — функция `sync_push`.** Пользователю (`authenticated`) выдан только `SELECT`, RLS
   показывает только свои строки (и в `sync_rows`, и в каждой таблице отдельно); `INSERT`/`UPDATE`/`DELETE` не выданы
   никому из ролей API. `sync_push` — `SECURITY DEFINER` с пустым `search_path`: пользователь берётся из токена
   (`auth.uid()`), а не из аргументов. `changes_since` выполняется с правами вызывающего — её ограничивает RLS.
   Миграции выполняются от роли `postgres` (владелец объектов приложения, не суперпользователь).
4. **`rev` — одна серверная последовательность на все таблицы**, курсор устройства — одно число. Отправки одного
   пользователя идут по очереди (advisory lock на пользователя в транзакции `sync_push`): `rev` пользователя
   фиксируются в порядке выдачи, и pull рядом с push не может увести курсор за ещё невидимый `rev`.
5. **Правила сервера** (одинаковы в `sync_push` и в `FakeSyncServer` для тестов):
   - `updatedAt` (и `deletedAt`) дальше 5 минут вперёд серверных часов подрезается до серверного времени;
   - last-writer-wins: изменение сохраняется, если его (`updatedAt`, `updatedBy`) не раньше сохранённого; строки
     `updatedBy` сравниваются побайтово, как в JavaScript;
   - **приём пищи (`mealLogs`), записанный другим устройством после курсора отправителя (`since`), не
     перезаписывается** — отправитель его не видел и должен сначала объединить элементы;
   - непринятое изменение возвращается вместе с версией сервера (`current`), принятое получает следующий `rev`.
6. **Слияние — только на клиенте, в одном месте (`merge`).** Сервер ничего не сливает: он лишь отказывается
   затереть то, чего устройство не видело. Слияние `items` в SQL отвергнуто — это второе воплощение того же правила
   на другом языке, которое разойдётся с первым. Номер базовой версии на каждой строке (оптимистичная блокировка)
   отвергнут: устройству пришлось бы хранить `rev` каждой строки, а одного курсора достаточно — всё, что не новее
   курсора, устройство уже видело.
7. **Правило клиента: строка без записи в `syncOutbox` не менялась на устройстве — её заменяет версия сервера;
   строка с записью решается `merge`.** Поэтому `updatedAt` несинхронизированной строки сравнивается только тогда,
   когда есть что сравнивать, а подрезанное сервером время возвращается на устройство эхом отправки. Исходы
   `merge(local, remote)`: локальная версия (остаётся в очереди); серверная (локальная правка проиграла — запись
   очереди снимается, проигравшая версия отдаётся в `conflicts` для журнала конфликтов #279); для приёма пищи —
   объединение `items` по `id` (элемент, изменённый с двух сторон, — с более поздним `updatedAt` элемента; поля
   записи — от более поздней версии). Объединение, которое отличается от обеих версий, — **новая версия этого
   устройства на миллисекунду позже обеих**: её нужно записать и отправить, и сервер примет её поверх своей.
8. **Tombstone на элементе приёма пищи — `deletedAt` на элементе** (ADR-0009, п. 5): `merge` сравнивает его как
   обычную правку элемента, поэтому объединение не возвращает удалённый продукт. Получатель пометки теперь есть;
   сам модуль nutrition пока удаляет элемент физически (ADR-0011, п. 9) — перейти на пометку и скрыть такие элементы
   при чтении он должен отдельной issue **до** включения синхронизации.
9. **Ответ на отправку применяется сразу** (`applyPushResult`): принятое снимается с очереди, непринятое решается
   тем же `merge` против `current`. Иначе устройство с отстающими часами осталось бы с правкой, которую сервер
   не взял, а pull не принёс бы победившую версию — её `rev` уже позади курсора.
10. **Pull tombstone удаляет строку на устройстве физически** — отправлять нечего, скрывать нечего. Tombstone,
    который устройство сделало само (`softDelete`), эхо не трогает: его очистка — правило ADR-0010 (после
    подтверждённой отправки и не раньше 90 дней), его выполняет движок (#279). Состояние устройства
    (`localOnly.ts`) не отправляется и с сервера не принимается никогда.
11. **Устройство после 90 дней офлайн** (`isFullSyncDue`, `staleAfterFullPull`): отправить всю очередь, получить
    всё с `rev` 0, удалить локальные строки, которых нет ни на сервере, ни в очереди. Устройство, которое ещё ни
    разу не синхронизировалось, под правило не попадает — его первая синхронизация обычная (иначе пропали бы данные,
    накопленные до появления очереди, ADR-0010). Срок жизни tombstone на сервере считается от времени сервера
    (`received_at`), а не от часов устройства; сама очистка на сервере — отдельная issue дорожки `infra`.
12. **«Заменить данные в облаке»** (`buildReplace`, отправка с `replace: true`): полный pull, затем каждая строка
    устройства отправляется как есть, а каждая живая строка сервера, которой на устройстве нет, получает tombstone.
    С `replace` сервер пропускает правила п. 5 (LWW и приём пищи): версия из копии старше серверной и иначе
    проиграла бы. `updatedAt` записей копии не меняется — «переписать время на сейчас» отвергнуто: модули показывают
    и сортируют по этому полю.
13. **Транспорт — тонкий `fetch`-клиент** (`core/sync/client.ts`), без SDK: `POST /rest/v1/rpc/sync_push` пачками по
    200 (сервер принимает до 500), `GET /rest/v1/rpc/changes_since?since=…` страницами по 500 (до 1000), пока
    страница не придёт неполной. Нет связи, 5xx, 408, 429 — повтор через 1, 2, 4 … секунд (не больше минуты), пять
    повторов; остальные ответы — сразу ошибка `SyncRequestError` с кодом сервера. Локальные данные транспорт не
    читает и не пишет.
14. **Миграции сервера — пронумерованные файлы `infra/supabase/migrations/NNNN_name.sql`**, только на добавление.
    `migrate.sh` применяет те, которых нет в журнале `public.lifeos_migrations`, каждую — одной транзакцией вместе
    с записью в журнале. Вызов из `deploy.sh` и проверка восстановления на этой схеме — #266.
15. **Правило границ `logic-is-pure` распространено на `src/core/sync/`**: протокол и транспорт не импортируют
    React, Dexie и `core/db.ts`. Исключения перечислены поимённо — DBCore-middleware (`outbox.ts`, `tombstones.ts`),
    миграция Dexie (`naturalKeys.ts`) и тесты.

## Последствия

- ✅ Правила конфликта живут в одном чистом модуле и покрыты таблицей сценариев ADR-0009 (п. 10) без сети и базы;
  движок (#279) только читает состояние, вызывает функции и исполняет планы (`SyncPlan`).
- ✅ Новое необязательное поле записи или элемента не требует миграции сервера и не теряется при синхронизации.
- ✅ Пользователь не может ни прочитать, ни записать чужую строку: записи нет ни у одной роли API, чтение закрыто
  RLS; это проверяет CI на двух пользователях через настоящий API.
- ⚠️ Новая таблица в `TABLE_NAMES` требует миграции с её серверной таблицей (падает
  `core/sync/serverSchema.test.ts`), иначе сервер отклонит всю пачку с этой таблицей. Сервер выкатывается раньше
  приложения.
- ⚠️ PostgREST не публикует разделы: через API видна только `sync_rows`, сами таблицы — для SQL (аналитика, копии).
- ⚠️ Сервер не проверяет содержимое `data` (кроме того, что это объект): схему знает клиент. Ограничения размера —
  только на ключ и `updatedBy`; предел размера записи при необходимости — отдельной миграцией.
- ⚠️ Слитому приёму пищи нужна ещё одна отправка: в той же синхронизации, если движок повторит push после pull,
  или в следующей.
- ⚠️ Устройство получает обратно и собственные отправленные версии (эхо): это лишний трафик при первой копии,
  зато подрезанное время доходит до устройства без отдельного пути. Фильтр «кроме моего устройства» — оптимизация
  на потом.
- ⚠️ LWW по часам устройств теряет правку устройства с отстающими часами — осознанно (ADR-0009); проигравшая
  версия попадает в журнал конфликтов (#279).
- ⚠️ `schemaVersion` клиента (ADR-0009, п. 8) протокол пока не передаёт, согласия и возраст (#278, #279) и границу
  бесплатного тарифа (#280) `sync_push` пока не проверяет — это следующие контракты; функция расширяется
  параметрами со значениями по умолчанию.
- ⚠️ Строки `settings`, пришедшие с сервера, несут `updatedAt` и `updatedBy`; локально записанные — по-прежнему
  только `{ key, value }` (ADR-0010).
- ❌ Изменить правило слияния — значит изменить и `merge`, и условие в `sync_push`, и `FakeSyncServer`; их
  согласованность держат таблица сценариев и `infra/supabase/tests/migrations.test.sh`.
