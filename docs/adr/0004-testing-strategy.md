# 0004. Стратегия тестирования

Статус: принято · 2026-11-04

## Контекст

Код пишут агенты, владелец его не читает построчно. Тесты — главный способ убедиться, что
поведение соответствует критериям приёмки, и не дать агенту сломать чужую работу.

## Решение — пирамида

| Уровень      | Инструмент                        | Что проверяет                            | Где                                               |
| ------------ | --------------------------------- | ---------------------------------------- | ------------------------------------------------- |
| Unit         | Vitest                            | чистая логика: правила, парсеры, расчёты | `src/**/logic/*.test.ts`, `src/core/**/*.test.ts` |
| Компонентные | Testing Library + fake-indexeddb  | экраны с реальной БД в памяти            | `src/modules/**/*.test.tsx`                       |
| E2E          | Playwright, Chrome, экран 360×740 | сквозные сценарии из критериев приёмки   | `e2e/*.spec.ts`                                   |

Правила:

- **TDD для логики**: сначала падающий тест по критерию приёмки, затем код.
- Каждый критерий приёмки issue (Given/When/Then) покрыт хотя бы одним тестом; имя теста повторяет критерий.
- Тесты описывают поведение, не реализацию; компоненты ищутся по ролям и тексту, а не по классам.
- **Порог покрытия** для `src/core` и `src/modules/*/logic`: 85% строк, 80% ветвей. CI падает ниже.
- Время в тестах фиксируется (`vi.setSystemTime` или дата аргументом), сеть мокается — тесты детерминированы.
- Каждая история с UI добавляет или расширяет E2E-сценарий.

## Последствия

- ✅ Логика проверяется за секунды, E2E ловит поломки интеграции модулей.
- ❌ E2E медленнее (~15 с на набор), поэтому в E2E — только ключевые пути, а не все ветки.
