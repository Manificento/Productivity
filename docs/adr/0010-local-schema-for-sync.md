# 0010. Локальная схема под синхронизацию: tombstone, очередь, версия

Статус: принято · 2026-11-15 · уточняет [ADR-0009](0009-backend-sync-health-data.md) (раздел «Синхронизация», п. 1, 2,
7, 8), контракт ядра #274

## Контекст

ADR-0009 решил, **что** нужно локальной базе для синхронизации: `deviceId`, tombstone вместо удаления, исходящая
очередь через DBCore-middleware, единая версия схемы. Он оставил открытым, **как** это уживается с тем, что уже есть:

- удалённая строка (tombstone) продолжает занимать уникальный индекс (`&date` у `sleepLogs`, `checkIns`, `weightLogs`,
  `&[programId+date]` у `plannedSessions`), а детерминированные `id` появятся только следующим контрактом. До него
  модуль после удаления создаёт запись с новым случайным `id` — и получил бы ошибку уникального ключа;
- read-middleware «как страховка» должна скрывать tombstone во всех чтениях, иначе каждый модуль пришлось бы
  переписывать сразу;
- резервная копия делает `clear()` + `bulkAdd` и ничего не знает ни об очереди, ни о `device.id`.

## Решение

1. **Tombstone для приложения — это отсутствие строки.** `softDelete(table, id)` / `softDeleteMany` (`core/db.ts`)
   ставят `deletedAt` и поднимают `updatedAt`. Middleware `core/sync/tombstones.ts` убирает такие строки из всех
   чтений через `db`: `get`, `bulkGet`, `toArray`, `where`, `count`, курсоры (`filter`, `each`, `keys`, `limit`,
   `offset`, `uniqueKeys`) и, значит, из `useLiveQuery`. `update` / `modify` находят строки через те же чтения и
   tombstone не меняют. Модули поле `deletedAt` не проверяют.
2. **Tombstone никогда не мешает записи: запись его заменяет.** Перед `add` / `put` middleware в той же транзакции
   физически удаляет tombstone, который держит первичный ключ новой строки (`add`) или её уникальный ключ под
   другим `id`. `put` с `id` самого tombstone просто перезаписывает его — так будут пересоздаваться записи с
   детерминированными `id` (ADR-0009, п. 5). Живая строка уникальный ключ держит как раньше.
   Подмена `id` новой строки на `id` tombstone отвергнута: модуль уже держит свой `id` и дальше обновлял бы
   несуществующую запись — тихая потеря правок.
3. **Запись в `syncOutbox` без строки в таблице — это удаление.** Очередь (`core/sync/outbox.ts`) хранит одну
   запись на строку — `{ table, key, updatedAt }`, первичный ключ `[table+key]`, последняя правка заменяет
   предыдущую, поэтому очередь не растёт быстрее данных. Middleware пишет её в той же транзакции для `add`, `put`,
   `modify`, `delete`, `bulk*`, удаления по диапазону и `clear`; сами строки она не меняет. Физическое удаление
   (в том числе tombstone из п. 2) тоже попадает в очередь, поэтому удаление не теряется: протокол отправки
   (следующий шаг ADR-0009) для ключа без строки шлёт tombstone с `deletedAt` = `updatedAt` записи очереди.
4. **Состояние устройства не синхронизируется.** Ключи `settings` из `core/sync/localOnly.ts`
   (`adaptation.morning`, `adaptation.onboardingDone`, `device.id`, `time.pomodoro.running`) в очередь не попадают;
   `softDelete` такого ключа — обычное удаление, tombstone ему не нужен. `device.id` (UUID) создаётся при открытии
   базы (`db.on('ready')`), в том числе после обновления со старой версии.
5. **`updatedBy` заполняет слой синхронизации**, а не модули и не middleware: при отправке — свой `device.id`, при
   получении — устройство-автор. Локально несинхронизированная строка поля не имеет.
6. **Резервная копия — только живые данные.** В экспорт не попадают tombstone, `syncOutbox` и `device.id`; остальные
   ключи состояния устройства экспортируются (восстановление на том же телефоне не показывает онбординг заново).
   Импорт сохраняет `device.id` устройства, игнорирует `device.id` и строки с `deletedAt` из файла; всё удалённое и
   восстановленное попадает в очередь — с аккаунтом это и есть «заменить данные в облаке» (ADR-0009, п. 9).
7. **Одна версия схемы.** `SCHEMA_VERSION` (`core/schemaVersion.ts`) — номер последней версии Dexie и версия
   резервной копии; база не запускается, если они разошлись. Версии Dexie остаются литералами (append-only).
   `importAll` принимает копии этой версии и старше (старые копии несут `1`), новее — отклоняет.

## Последствия

- ✅ Модули не меняются, кроме замены `delete` на `softDelete`; это проверяет `core/softDelete.guard.test.ts`.
- ✅ Удаление и повторное создание на тот же день работает уже сейчас, до детерминированных `id`.
- ⚠️ До контракта с детерминированными `id` пересозданная запись получает новый `id`: на сервер уйдут удаление
  старого `id` и новая запись. Миграция того контракта сведёт их в один `id`.
- ⚠️ `count()` и запросы только ключей читают строки целиком (иначе tombstone не отличить). Для таблиц LifeOS это
  сотни–тысячи строк; если станет заметно — разрежённый индекс `deletedAt` отдельным контрактом.
- ⚠️ Каждая `readwrite`-транзакция захватывает `syncOutbox`, поэтому пишущие транзакции разных модулей идут по
  очереди (так же устроен Dexie Cloud).
- ⚠️ `Setting.updatedAt` — пока только поле типа: модули пишут `{ key, value }`, и middleware строки не меняет.
  Время изменения настройки до синхронизации берётся из записи очереди; кто заполняет поле в самой строке
  (middleware ядра или общий хелпер записи настроек) — отдельная issue: это меняет форму строк `settings` в базе и в
  экспорте, которую сейчас фиксируют тесты модулей, и в критерии #274 не входило.
- ❌ Middleware работает на внутреннем уровне Dexie (DBCore): обновление Dexie требует прогнать
  `core/sync/*.test.ts`. В middleware только `.then()`-цепочки — `async/await` теряет зону транзакции Dexie.
