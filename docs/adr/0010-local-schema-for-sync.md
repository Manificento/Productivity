# 0010. Локальная схема под синхронизацию: tombstone, очередь, версия

Статус: принято · 2026-11-15 · уточняет [ADR-0009](0009-backend-sync-health-data.md) (раздел «Синхронизация», п. 1, 2,
7, 8), контракт ядра #274

## Контекст

ADR-0009 решил, **что** нужно локальной базе для синхронизации: `deviceId`, tombstone вместо удаления, исходящая
очередь через DBCore-middleware, единая версия схемы. Он оставил открытым, **как** это уживается с тем, что уже есть:

- удалённая строка (tombstone) продолжает занимать уникальный индекс (`&date` у `sleepLogs`, `checkIns`, `weightLogs`,
  `&[programId+date]` у `plannedSessions`), а детерминированные `id` появятся только следующим контрактом. До него
  модуль после удаления создаёт запись с новым случайным `id` — и получил бы ошибку уникального ключа;
- если tombstone — это вся строка с пометкой, то удалённое пользователем (текст заметки, сон, вес, еда) остаётся на
  устройстве навсегда и при первой отправке уходит в облако — в том числе удалённое **до** согласия на облако;
- read-middleware «как страховка» должна скрывать tombstone во всех чтениях, иначе каждый модуль пришлось бы
  переписывать сразу;
- резервная копия делает `clear()` + `bulkAdd` и ничего не знает ни об очереди, ни о `device.id`.

## Решение

1. **Tombstone для приложения — это отсутствие строки, и содержимого в нём нет.** `softDelete(table, id)` /
   `softDeleteMany` (`core/db.ts`) в одной транзакции **заменяют** строку на минимальную: первичный ключ, `createdAt`
   (если был), `updatedAt` = `deletedAt` = время удаления (для `settings` — `{ key, updatedAt, deletedAt }`).
   Остальные поля стираются сразу: синхронизации для передачи удаления нужны только ключ и два времени, а удалённое
   пользователем не должно ни лежать на устройстве, ни уйти в облако (согласие ADR-0009 даётся на данные, а не на
   то, что человек уже удалил). Middleware `core/sync/tombstones.ts` убирает такие строки из всех чтений через
   `db`: `get`, `bulkGet`, `toArray`, `where`, `count`, курсоры (`filter`, `each`, `keys`, `limit`, `offset`,
   `uniqueKeys`) и, значит, из `useLiveQuery`. `update` / `modify` находят строки через те же чтения и tombstone не
   меняют. Модули поле `deletedAt` не проверяют.
   Вариант «оставить строку целиком и чистить позже» отвергнут: нужны правило и срок очистки, а до очистки
   содержимое всё равно попадает в отправку.
2. **Tombstone никогда не мешает записи.** Tombstone от `softDelete` не несёт полей, поэтому не занимает ни один
   индекс, кроме первичного ключа: уникальный ключ (`&date`, `&[programId+date]`) свободен сразу. На остальные
   случаи middleware перед `add` / `put` в той же транзакции физически удаляет tombstone, который держит первичный
   ключ новой строки (`add`) или — если tombstone пришёл целой строкой с `deletedAt` (так его может доставить
   pull) — её уникальный ключ под другим `id`. `put` с `id` самого tombstone просто перезаписывает его — так будут
   пересоздаваться записи с детерминированными `id` (ADR-0009, п. 5). Живая строка уникальный ключ держит как
   раньше. Подмена `id` новой строки на `id` tombstone отвергнута: модуль уже держит свой `id` и дальше обновлял
   бы несуществующую запись — тихая потеря правок.
3. **Запись в `syncOutbox` без строки в таблице — это удаление.** Очередь (`core/sync/outbox.ts`) хранит одну
   запись на строку — `{ table, key, updatedAt }`, первичный ключ `[table+key]`, последняя правка заменяет
   предыдущую, поэтому очередь не растёт быстрее данных. Middleware пишет её в той же транзакции для `add`, `put`,
   `modify`, `delete`, `bulk*`, удаления по диапазону и `clear`; сами строки она не меняет. Физическое удаление
   (в том числе tombstone из п. 2) тоже попадает в очередь, поэтому удаление не теряется: протокол отправки
   (следующий шаг ADR-0009) для ключа без строки шлёт tombstone с `deletedAt` = `updatedAt` записи очереди, а для
   ключа с tombstone — сам tombstone: ключ и времена, без содержимого.
4. **Состояние устройства не синхронизируется.** Ключи `settings` из `core/sync/localOnly.ts`
   (`adaptation.morning`, `adaptation.onboardingDone`, `device.id`, `time.pomodoro.running`) в очередь не попадают;
   `softDelete` такого ключа — обычное удаление, tombstone ему не нужен. `device.id` (UUID) создаётся при открытии
   базы (`db.on('ready')`), в том числе после обновления со старой версии.
5. **`updatedBy` заполняет слой синхронизации**, а не модули и не middleware: при отправке — свой `device.id`, при
   получении — устройство-автор. Локально несинхронизированная строка поля не имеет.
6. **Резервная копия — только живые данные.** В экспорт не попадают tombstone, `syncOutbox` и `device.id`; остальные
   ключи состояния устройства экспортируются (восстановление на том же телефоне не показывает онбординг заново).
   Импорт сохраняет `device.id` устройства, игнорирует `device.id` и строки с `deletedAt` из файла; всё удалённое и
   восстановленное попадает в очередь — с аккаунтом это и есть «заменить данные в облаке» (ADR-0009, п. 9).
7. **Одна версия схемы.** `SCHEMA_VERSION` (`core/schemaVersion.ts`) — номер последней версии Dexie и версия
   резервной копии; база не запускается, если они разошлись. Версии Dexie остаются литералами (append-only).
   `importAll` принимает копии этой версии и старше (старые копии несут `1`), новее — отклоняет.
   Цена: номер в файле копии прыгает с `1` на `7`, хотя формат файла не менялся, и дальше растёт с каждой версией
   Dexie. Приложение, которое ещё не обновилось (другой телефон, старая вкладка), такую копию не примет — сначала
   обновить приложение, потом восстанавливать; текст ошибки импорта говорит именно это. Принято осознанно: одна
   версия проще двух, а копию из более новой схемы старое приложение молча читать не должно.

## Последствия

- ✅ Модули не меняются, кроме замены `delete` на `softDelete`; это проверяет `core/softDelete.guard.test.ts`.
- ✅ Удаление и повторное создание на тот же день работает уже сейчас, до детерминированных `id`.
- ⚠️ До контракта с детерминированными `id` пересозданная запись получает новый `id`: на сервер уйдут удаление
  старого `id` и новая запись. Миграция того контракта сведёт их в один `id`.
- ⚠️ `count()` и запросы только ключей читают строки целиком (иначе tombstone не отличить). Для таблиц LifeOS это
  сотни–тысячи строк; если станет заметно — разрежённый индекс `deletedAt` отдельным контрактом.
- ⚠️ Каждая `readwrite`-транзакция захватывает `syncOutbox`, поэтому пишущие транзакции разных модулей идут по
  очереди (так же устроен Dexie Cloud).
- ⚠️ `Setting.updatedAt` — пока только поле типа: модули пишут `{ key, value }`, и middleware строки не меняет.
  Время изменения настройки до синхронизации берётся из записи очереди; кто заполняет поле в самой строке
  (middleware ядра или общий хелпер записи настроек) — отдельная issue: это меняет форму строк `settings` в базе и в
  экспорте, которую сейчас фиксируют тесты модулей, и в критерии #274 не входило.
- ⚠️ **Tombstone на устройстве не чистится.** Он хранит только ключ и времена, но копится; сейчас его убирает лишь
  импорт копии или демо-данных (`clear()`). Правило очистки — после подтверждённой отправки и не раньше срока
  жизни tombstone на сервере (90 дней, ADR-0009, п. 2 и 6) — решает контракт протокола отправки.
- ⚠️ **В очереди только то, что менялось после v7.** Обновление до v7 создаёт пустой `syncOutbox`; всё, что
  пользователь накопил раньше (и любая строка, не тронутая после обновления), в очередь не попадёт. Поэтому первая
  синхронизация аккаунта **не может слать одну очередь**: она отправляет (или ставит в очередь хелпером ядра
  «пометить всё») каждую живую строку каждой таблицы из `TABLE_NAMES`, кроме ключей состояния устройства. Это
  условие контракта входа в аккаунт / первой отправки.
- ⚠️ **Pull не должен возвращаться в очередь.** Middleware записывает в `syncOutbox` любое изменение, в том числе
  строки, которые слой синхронизации сам положит при получении; без обхода каждая полученная строка ушла бы
  обратно, сервер дал бы ей новый `rev`, остальные устройства получили бы её снова — бесконечный пинг-понг.
  Решение для контракта pull: слой синхронизации пишет полученное в транзакции, **помеченной в ядре** (хелпер в
  `core/sync/outbox.ts` запоминает DBCore-транзакцию, `trackMutations` для неё ничего не записывает). Помечается
  транзакция, а не таблица или строка, поэтому одновременная запись модуля попадает в очередь как обычно.
  Tombstone-middleware в такой транзакции работает как всегда. Вариант «писать в обход `db` вторым соединением»
  отвергнут: живые запросы не увидели бы полученных строк. В #274 кода для этого нет — только это решение.
- ⚠️ **Список состояния устройства неполон.** Критерии #274 фиксируют четыре ключа. Кандидаты, которые описывают
  именно это устройство, но пока идут в очередь: `health.alarm` и `health.alarm.dismissal` (будильник, заведённый
  на этом телефоне) и `health.import`, `health.import.dismissed`, `health.import.workouts` (состояние импорта из
  Health Connect / HealthKit на этом телефоне). Решить по каждому и дополнить `LOCAL_ONLY_SETTING_KEYS` нужно
  отдельной `type:contract` issue **до** протокола отправки — иначе будильник одного телефона приедет на другой.
  (`lifeos.time.pomodoro.state` в этот список не входит: это `localStorage`, а не `settings`, в очередь он не
  попадает.)
- ❌ Middleware работает на внутреннем уровне Dexie (DBCore): обновление Dexie требует прогнать
  `core/sync/*.test.ts`. В middleware только `.then()`-цепочки — `async/await` теряет зону транзакции Dexie.
