# 0009. Бэкенд, синхронизация и право на данные о здоровье

Статус: **предложено (черновик)** · 2026-11-04 · ждёт решения владельца продукта. До одобрения PR не сливается,
данные по-прежнему не покидают устройство ([SPEC 0.3](../SPEC.md), раздел 2).

## Контекст

SPEC 0.3 и [product-decisions.md](../product-decisions.md) ставят облако в веху M8: аккаунт, облачная копия,
синхронизация между устройствами, аналитика, граница freemium, затем AI-коуч и модели на данных всех
пользователей. Модель данных остаётся **local-first** ([ADR-0001](0001-local-first-pwa.md),
[ADR-0008](0008-web-and-native-one-codebase.md)): IndexedDB через Dexie на вебе, Android и iOS; облако — копия и
синхронизация поверх, не замена.

Что уже есть в коде и что важно для выбора:

- ~20 таблиц Dexie (`src/core/db.ts`), у записей `id` (UUID с устройства), `createdAt`, `updatedAt`
  (`src/core/ids.ts`). Удаление сейчас **физическое**; у таблицы `settings` нет `updatedAt`.
- Модули пишут только в свои таблицы ([architecture.md](../architecture.md)); общий путь записи — `src/core/logging/`.
- Данные о здоровье (сон, питание, тренировки, чек-ины, тесты внимания) — основная ценность продукта и
  одновременно самая чувствительная категория.
- Будущие AI-коуч и «модели на данных всех пользователей» требуют, чтобы сервер мог читать данные
  (с согласия), то есть полностью сквозное шифрование всего не подходит.
- Первая аудитория — Казахстан и СНГ, позже ЕС; приложение будет в Google Play и App Store (ADR-0008).

## Рассмотренные варианты

| Критерий                                    | A. BaaS (Supabase/Postgres) + свой протокол по `updatedAt` | B. Движок синхронизации поверх Dexie (Dexie Cloud)             | C. Собственный сервер (Node + Postgres)      |
| ------------------------------------------- | ---------------------------------------------------------- | -------------------------------------------------------------- | -------------------------------------------- |
| Работы до первой синхронизации              | средне: auth и БД готовы, протокол синхронизации свой      | **мало**: аддон к Dexie, офлайн-очередь и конфликты из коробки | много: auth, API, БД, протокол, эксплуатация |
| Конфликты, tombstone, офлайн-очередь        | пишем сами (~1 модуль `src/core/sync/`, тестируемый)       | готовые                                                        | пишем сами                                   |
| Аналитика и AI на данных всех пользователей | **SQL по Postgres напрямую**, RLS, представления           | данные в формате сервиса; выгрузка отдельно                    | SQL, но всё своё                             |
| Хранение в Казахстане (локализация)         | **да**: Supabase — open source, разворачивается в ЦОД в РК | только платная self-hosted лицензия                            | да                                           |
| Зависимость от поставщика                   | низкая (Apache 2.0, стандартный Postgres)                  | высокая (протокол и сервер — продукт одной компании)           | нет                                          |
| Стоимость на старте                         | низкая (свой сервер/VPS или их облако для ЕС)              | подписка или лицензия                                          | время команды                                |
| Риск для качества кода агентами             | средний: протокол — чистые функции + тесты                 | низкий                                                         | высокий: много инфраструктуры                |

Также смотрели PowerSync и ElectricSQL (синхронизация Postgres ↔ SQLite): локальная БД у нас IndexedDB/Dexie,
переход на SQLite — это переписать слой данных всех модулей; отложено.

## Решение (предлагается)

**Вариант A: Postgres на Supabase (self-hosted для данных пользователей из РК) + собственный тонкий протокол
синхронизации в `src/core/sync/`.**

Почему не B: Dexie Cloud даёт самый быстрый старт, но аналитика и AI-коуч — часть продукта, а не побочный
эффект, и для них нужен открытый SQL-доступ к данным; требование локализации в РК ведёт к self-hosted
лицензии и зависимости от одной компании. Почему не C: та же функциональность, что у A, но auth, хранилище и
админка — своими руками; это не та работа, которую стоит делать до первых платящих пользователей.

Вариант B остаётся запасным: если свой протокол окажется дороже ожидаемого (критерий — две вехи без
стабильной синхронизации), пересматриваем.

## Синхронизация

**Модель.** Каждая синхронизируемая таблица на сервере — та же форма записи плюс `user_id`, `rev` и `deleted_at`.
Клиент хранит курсор `lastPulledRev` и исходящую очередь.

1. **Изменения на устройстве.** Запись через существующие функции модулей ставит `updatedAt` (как сейчас)
   и добавляет `{table, id}` в таблицу-очередь `syncOutbox` (хук Dexie в ядре, модули не меняются).
2. **Удаление — tombstone.** Физическое удаление заменяется на `deletedAt` (хелпер в ядре; модули вызывают
   его вместо `delete`); чтение по умолчанию скрывает удалённые. Tombstone хранится 90 дней, затем сервер
   его вычищает; устройство, не синхронизировавшееся дольше, делает полную пересинхронизацию.
3. **Push.** Очередь отправляется пачками; сервер записывает, присваивает `rev` из своей последовательности
   (единое серверное время, а не часы устройства) и отвечает новым `rev`.
4. **Pull.** `GET changes?since=lastPulledRev` — все записи пользователя с `rev` больше курсора, включая tombstone.
5. **Конфликты.** Last-writer-wins **по записи** по `updatedAt`, при равенстве — по `deviceId`. Сервер не
   принимает `updatedAt` из будущего больше чем на 5 минут (часы устройства). Журналы (`habitLogs`,
   `timeEntries`, `sleepLogs`, `mealLogs`, `checkIns`…) почти не конфликтуют: новые записи — новые `id`.
   Для `settings` ключ становится `id`, добавляется `updatedAt`. Слияние по полям — только если LWW
   на практике теряет данные (метрика: жалобы/тесты), отдельным ADR.
6. **Офлайн.** Очередь живёт в IndexedDB; синхронизация при старте, при возвращении сети и раз в N минут;
   ошибки сети — повтор с экспоненциальной задержкой, данные на устройстве не трогаются.
7. **Миграции.** Версия схемы Dexie (`this.version(n)`) и версия схемы сервера идут вместе; клиент шлёт
   `schemaVersion`. Миграции только добавляющие (новые поля — необязательные). Сервер отклоняет клиента
   старее минимальной версии с ответом «обновите приложение»; формат резервной копии (`BACKUP_VERSION`) —
   тот же номер.
8. **Тесты.** Протокол — чистые функции (`merge`, `applyPull`, `buildPush`) с таблицей сценариев:
   два устройства, офлайн, удаление против правки, часы в будущем. Интеграционный тест — против локального
   Postgres в CI.

## Данные о здоровье: право и согласие

> ⚠️ Ниже — понимание требований на 2026-11 для технического дизайна, **не юридическое заключение**.
> До запуска облака нужна проверка юристом по РК и ЕС (задача владельца, P2).

**Согласие.** Отдельный экран до первой отправки данных: что отправляется, зачем (копия, синхронизация,
отдельно — аналитика и AI), где хранится, как удалить. Согласие на облачную копию и согласие на использование
обезличенных данных для моделей — **разные галочки**; без согласия приложение полностью работает локально.
Факт и версия согласия хранятся на сервере.

**Казахстан.** Закон РК «О персональных данных и их защите» (№ 94-V от 21.05.2013): согласие субъекта на сбор
и обработку; требование хранить базу с персональными данными граждан РК на территории РК; уведомление об
утечках уполномоченному органу. Сведения о здоровье дополнительно относятся к медицинской тайне по Кодексу
о здоровье. Следствие для дизайна: **сервер для пользователей из РК — в ЦОД на территории РК** (поэтому
self-hosted Postgres/Supabase).

**ЕС (GDPR).** Данные о здоровье — особая категория (ст. 9): нужно явное согласие; оценка воздействия (DPIA,
ст. 35); права доступа, удаления и переносимости (ст. 15, 17, 20) — экспорт JSON уже есть, удаление аккаунта
с данными — обязательно; передача данных за пределы ЕС (гл. V) требует оснований (например, стандартных
договорных условий), поэтому для пользователей из ЕС — отдельный регион хранения в ЕС; представитель в ЕС
(ст. 27), если компания не там.

**Сторы.** Google Play: политика приложений о здоровье и разрешения Health Connect (декларация в консоли,
данные Health Connect — только для заявленных функций), раздел Data safety. App Store: правило 5.1.3 —
данные HealthKit нельзя использовать для рекламы и продавать, политика конфиденциальности обязательна,
метки App Privacy. Импорт из Health Connect/HealthKit (M7) включается в облако только после этих деклараций.

**Хранение и шифрование.** TLS везде; шифрование диска и бэкапов БД на сервере; Row Level Security —
пользователь видит только свои строки; доступ сотрудников — через аудитируемую роль. Таблицы о здоровье
дополнительно шифруются на уровне полей ключом сервиса (KMS). Сквозное шифрование «только у пользователя»
не выбрано: оно исключает AI-коуча на сервере; можно вернуться к нему как к платной опции «приватный режим».

**Удаление.** «Удалить аккаунт» стирает данные на сервере в течение 30 дней (включая бэкапы по их циклу),
локальные данные остаются на устройстве, пока пользователь их не сотрёт.

## Freemium и флаги функций

| Бесплатно                                            | По подписке                                                     |
| ---------------------------------------------------- | --------------------------------------------------------------- |
| Все трекеры, локальное хранение, экспорт/импорт JSON | Облачная копия и синхронизация между устройствами               |
| Важные события и базовая адаптация дня               | Полная персонализация (эластичные границы), расширенные инсайты |
| Базовые инсайты (ограниченное окно/число корреляций) | AI-коуч                                                         |

Граница — предложение; точную границу решает владелец ([product-decisions.md](../product-decisions.md), открытые
вопросы).

**Механизм.** `src/core/features.ts`: `useFeature('sync' | 'insightsPro' | 'coach' …)`. Источник — права
(entitlements) из подписанного токена сервера, кэшируются локально с периодом отсрочки 7 дней без сети;
без аккаунта — набор бесплатных функций. Модули спрашивают флаг, а не тариф. Оплата: в нативных приложениях —
покупки внутри сторов (их правила для цифровых подписок), на вебе — платёжный провайдер; сервер сводит всё к
одним правам.

## Последствия

- ✅ Данные остаются на устройстве и работают офлайн; облако добавляется, ничего не ломая.
- ✅ Открытый Postgres: аналитика и будущие модели — SQL, без выгрузок из чужого формата.
- ✅ Хранение в РК и в ЕС — разные развёртывания одного стека.
- ⚠️ Протокол синхронизации — наш код: нужен отдельный контракт ядра и сильные тесты (раздел «Синхронизация», п. 8).
- ⚠️ Переход на tombstone меняет удаление во всех модулях — отдельные issues по модулям после контракта ядра.
- ⚠️ Эксплуатация self-hosted Supabase в РК — работа и деньги; решение о хостинге — за владельцем.
- ❗ Юридическая проверка (РК, ЕС, сторы) — обязательна до первой отправки данных.
