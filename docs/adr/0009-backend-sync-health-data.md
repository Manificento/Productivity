# 0009. Бэкенд, синхронизация и право на данные о здоровье

Статус: **принято с решениями владельца** · 2026-11-04 · решения записаны в разделе «Решения владельца». Данные
по-прежнему не покидают устройство до вехи M8 ([SPEC 0.3](../SPEC.md), раздел 2); юридический разбор — раздел
«Данные о здоровье».

## Контекст

SPEC 0.3 и [product-decisions.md](../product-decisions.md) ставят облако в веху M8: аккаунт, облачная копия,
синхронизация между устройствами, аналитика, граница freemium, затем AI-коуч и модели на данных всех
пользователей. Модель данных остаётся **local-first** ([ADR-0001](0001-local-first-pwa.md),
[ADR-0008](0008-web-and-native-one-codebase.md)): IndexedDB через Dexie на вебе, Android и iOS; облако — копия и
синхронизация поверх, не замена.

Что есть в коде сейчас и что важно для выбора:

- 14 таблиц Dexie (`src/core/db.ts`, `TABLE_NAMES`; ещё 7 запланировано в SPEC 5.6), схема Dexie — версия 2.
  У записей `id` (UUID с устройства), `createdAt`, `updatedAt` (`src/core/ids.ts`). У `settings` первичный ключ —
  `key`, `updatedAt` нет.
- Удаление сейчас **физическое**. Резервная копия (`src/core/backup.ts`, `BACKUP_VERSION = 1`) при импорте делает
  `clear()` + `bulkAdd` всех таблиц.
- Часть журналов — «одна запись на день» по естественному ключу: `sleepLogs` и `checkIns` (уникальный индекс
  `&date`), `habitLogs` (одна на `[habitId+date]`, правило в `habits/data/habitStore.ts`), `mealLogs` (одна на
  дату и приём пищи, `health/data/food.ts`); запланированный `weightLogs` — тоже по дате.
- Модули пишут в свои таблицы в явных транзакциях только по своим таблицам (например,
  `db.transaction('rw', db.checkIns, …)`).
- Данные о здоровье (сон, питание, тренировки, чек-ины, тесты внимания) — основная ценность продукта и
  одновременно самая чувствительная категория.
- AI-коуч и «модели на данных всех пользователей» требуют, чтобы сервер мог читать данные (с согласия), то есть
  сквозное шифрование всего не подходит.
- **Рынки (решение владельца, 2026-11-04).** Закрытые тесты — в Казахстане; публичный запуск — общемировой
  (ЕС, США и другие страны). Регион хранения выбирается по этому плану (см. «Решение»), а не по одной стране.

## Рассмотренные варианты

| Критерий                                   | A. BaaS (Supabase/Postgres) + свой протокол                          | B. Движок синхронизации поверх Dexie (Dexie Cloud)             | C. Собственный сервер (Node + Postgres)      |
| ------------------------------------------ | -------------------------------------------------------------------- | -------------------------------------------------------------- | -------------------------------------------- |
| Работы до первой синхронизации             | средне: auth и БД готовы, протокол синхронизации свой                | **мало**: аддон к Dexie, офлайн-очередь и конфликты из коробки | много: auth, API, БД, протокол, эксплуатация |

| Риск для качества кода агентами            | средний: протокол — чистые функции + тесты                           | низкий                                                         | высокий: много инфраструктуры                |

Также смотрели PowerSync (синхронизация Postgres ↔ SQLite на клиенте: локальная БД у нас IndexedDB/Dexie, переход на
SQLite — это переписать слой данных всех модулей) и ElectricSQL. Текущий Electric отдаёт «shapes» по HTTP в любой
клиентский стор и не требует SQLite — его стоит **проверить как канал pull** для варианта A (запись — через наш push).

## Решение

**Вариант A: Postgres на Supabase + собственный тонкий протокол синхронизации в `src/core/sync/`.** Хостинг (решение
владельца от 2026-11-05): **облако с первого дня, включая Казахстан, самый дешёвый вариант, удовлетворяющий ст. 12
закона № 94-V.** У облачного Supabase нет региона в Казахстане, поэтому продакшен — **Supabase self-hosted (Docker)
на виртуальном сервере в дата-центре на территории РК**; пока регион один, этот инстанс обслуживает всех
пользователей (для жителей ЕС прямой сбор данных контролёром из РК не является трансграничной передачей — EDPB
05/2021, пример 1). Устройство — **ячейки по регионам** (решение владельца 7 ниже): следующий регион — отдельное
развёртывание со своими базой и Auth. Облачный
Supabase Free в регионе ЕС — только для разработки и staging с синтетическими данными, никогда с данными реальных
пользователей. Переезд на управляемый Postgres (Yandex Cloud kz1) или отдельный регион ЕС для доверия европейских
пользователей — когда нагрузка или бизнес этого потребуют; стек один, меняется только развёртывание. Цены и
кандидаты — в разделе «Хостинг в Казахстане».

Почему не B: самый быстрый старт, но аналитика и модели — часть продукта, а не побочный эффект, и нужен открытый
SQL-доступ; требование локализации ведёт к self-hosted лицензии и зависимости от одной компании. Почему не C: та же
функциональность, что у A, но auth, хранилище и админка — своими руками.

Вариант B остаётся запасным: если свой протокол окажется дороже ожидаемого (критерий — две вехи без стабильной
синхронизации), пересматриваем.

## Синхронизация

**Модель.** Каждая синхронизируемая таблица на сервере — та же форма записи плюс `user_id`, `rev` (серверная
последовательность), `deleted_at`, `updated_by` (`deviceId`). Клиент хранит курсор `lastPulledRev`, свой `deviceId`
и исходящую очередь.

1. **Изменения на устройстве.** Запись через существующие функции модулей ставит `updatedAt` (как сейчас).
   Обычный хук Dexie здесь не подходит: он может писать только в таблицы текущей транзакции, а модули открывают
   транзакции по своим таблицам. Поэтому — **DBCore-middleware в ядре** (`db.use({ stack: 'dbcore' })`), которая
   добавляет `syncOutbox` в каждую `readwrite`-транзакцию и записывает туда `{table, key}` изменённых строк
   (так устроен и Dexie Cloud). Модули при этом не меняются.
2. **Удаление — tombstone.** Физическое удаление заменяется на `deletedAt` (хелпер в ядре; модули вызывают его
   вместо `delete`). Фильтра «по умолчанию» в Dexie нет: удалённые скрываются **отдельными issue по модулям** (все
   `where`/`toArray`/`count`/`useLiveQuery`) плюс read-middleware в ядре как страховка. Уникальные индексы
   (`&date`) удалённая строка продолжает занимать — поэтому для таблиц с естественным ключом удаление и повторное
   создание работают через тот же `id` (п. 5). Tombstone хранится на сервере 90 дней.
3. **Push.** Очередь отправляется пачками; сервер записывает, присваивает `rev` и отвечает им. `updatedAt` из
   будущего (больше 5 минут вперёд серверного времени) **не отклоняется, а подрезается** до серверного времени —
   иначе запись навсегда застрянет в очереди.
4. **Pull.** `GET changes?since=lastPulledRev` — все записи пользователя с `rev` больше курсора, включая tombstone.
   Курсор — серверный `rev`, а не часы устройства.
5. **Конфликты.**
   - Обычные записи: **last-writer-wins по записи** по `updatedAt`, при равенстве — по `updated_by`.
   - **Таблицы с естественным ключом** (`sleepLogs`, `checkIns`, `habitLogs`, `mealLogs`, позже `weightLogs`):
     одна и та же дата, записанная офлайн на двух устройствах, иначе даёт две записи с разными `id` — на `&date`
     это ошибка ограничения и остановка pull, а без уникального индекса — тихие дубли. Решение: **детерминированный
     `id` из естественного ключа** (`checkIn:<DateKey>`, `sleep:<DateKey>`, `habitLog:<habitId>:<DateKey>`,
     `meal:<DateKey>:<kind>`), тогда это одна запись и работает обычный LWW. Существующие записи переводятся
     миграцией Dexie (новая версия схемы, копирование с новым `id`); если несколько старых записей сходятся в один
     `id` (дубли уже бывают, например у `habitLogs` после импорта), остаётся запись с наибольшим `updatedAt`, остальные
     удаляются (для `mealLogs` — объединение `items`, см. ниже).
   - **`mealLogs` — слияние списка, а не LWW.** Приём пищи — растущий список `items[]` (`addMealItem` дописывает в
     запись даты и приёма). Если телефон и ноутбук офлайн добавят по продукту в `meal:<DateKey>:lunch`, LWW по записи
     гарантированно потеряет один из них. Правило: у каждого элемента свой `id`; слияние — **объединение `items` по
     `id`**, правка элемента — LWW по элементу (`updatedAt` элемента), удаление элемента — tombstone на элементе.
     Сценарий «два устройства добавляют в один приём пищи» — в таблице тестов (п. 10).
   - Слияние по полям для остальных таблиц — только если LWW на практике теряет данные, отдельным ADR.
6. **Офлайн.** Очередь живёт в IndexedDB; синхронизация при старте, при возвращении сети и раз в N минут; ошибки
   сети — повтор с экспоненциальной задержкой, данные на устройстве не трогаются. Устройство, не синхронизировавшееся
   дольше срока жизни tombstone (90 дней): сначала **push всей очереди**, затем полный pull, затем удаление локальных
   записей, которых нет на сервере и нет в очереди — иначе вернутся записи, удалённые на другом устройстве.
7. **Настройки.** `settings` сохраняет первичный ключ `key` (сменить первичный ключ таблицы Dexie нельзя без
   новой таблицы), добавляется `updatedAt`. Ключи состояния **устройства** не синхронизируются: список в ядре
   (сейчас — `adaptation.morning` с пропущенными шагами утра, `adaptation.onboardingDone`); синхронизируются
   настройки пользователя (`adaptation.baseline`, `time.pomodoro` после #101 и т. п.).
8. **Миграции.** Клиент шлёт `schemaVersion`; миграции только добавляющие (новые поля — необязательные); сервер
   отклоняет клиента старее минимальной версии с ответом «обновите приложение». Сейчас версия Dexie (2) и
   `BACKUP_VERSION` (1) расходятся, а `importAll` отклоняет копии новее своей версии — при введении синхронизации
   версии сводятся в одну `schemaVersion` с правилом совместимости для старых копий.
9. **Восстановление из копии при включённой синхронизации.** `importAll` делает `clear()` + `bulkAdd`: это не
   создаёт tombstone и не попадает в очередь, поэтому после восстановления следующий pull вернул бы данные сервера, а
   восстановленные записи могли бы не уйти на сервер. Правило: при включённом аккаунте восстановление —
   **явное действие «заменить данные в облаке»**: импорт помечает все записи в очередь, а отсутствующие в копии
   записи сервера получают tombstone. Без аккаунта импорт работает как сейчас.
10. **Тесты.** Протокол — чистые функции (`merge`, `applyPull`, `buildPush`) с таблицей сценариев: два устройства;
    офлайн; удаление против правки; часы в будущем; **один и тот же день на двух устройствах**; **два устройства добавляют в один приём пищи**; устройство после
    90 дней офлайн; восстановление копии. Интеграционный тест — против локального Postgres в CI.

### Следствия для дизайна (обязательные)

1. **Облако с первого дня, база — на территории РК.** Продакшен-инстанс стоит в дата-центре в Казахстане, поэтому ст. 12
   закона № 94-V выполняется для жителей РК буквально, а не через исключения. Резервные копии базы хранятся тоже в РК
   (объектное хранилище казахстанского провайдера). Данные реальных пользователей никогда не попадают в staging за
   пределами РК. Открытый вопрос для консультации остаётся только один: нужна ли регистрация в реестре операторов.
2. **Согласия.** Отдельные журналируемые согласия на (а) облачную копию и синхронизацию, (б) аналитику и модели на
   псевдонимизированных данных, (в) любую передачу третьим лицам. Ни одно — через общие условия использования (стандарт
   WA, ст. 8 РК, ст. 9 GDPR). Факт, версия текста и время согласия хранятся на сервере; отзыв — прекращение за 15 рабочих
   дней (РК) и удаление пользователя из обучающих наборов (ст. 17 GDPR); судьба уже обученных моделей — открытый вопрос.
3. **Ноль сторонних аналитических и рекламных SDK с доступом к событиям о здоровье.** Аналитика (CL5) — только
   собственная, first-party, по согласию (б). Иначе каждая передача — breach по правилу FTC.
4. **Процесс инцидентов** под самый жёсткий срок: регулятору РК за 1 рабочий день, ЕС за 72 часа, пользователям в США
   за 60 дней. Шифрование at rest и в клиенте снижает обязанность уведомлять субъектов (GDPR ст. 34(3)(a)). Договор с
   Supabase как с процессором обязывает его уведомлять нас.
5. **Freemium не завязан на доступ к HealthKit / Health Connect** (Apple 5.1.1(ii)): платная функция — синхронизация,
   не импорт из часов. Данные из HealthKit / Health Connect исключены из обучения моделей, пока это не разрешено
   явным согласием в рамках «improving health management» и Limited Use.
6. **Возраст** (решение владельца от 2026-11-05). Облачный аккаунт — с 16 лет (верхний порог ЕС, покрывает COPPA и
   большинство стран); в РК — с 18 лет или с согласия законного представителя (закон № 94-V возраста не задаёт, ГК даёт
   18). Младше — приложение работает local-first без аккаунта, ничего не собирается.
7. **Представитель в ЕС и DPIA** — до публичного запуска в ЕС; UK — отдельный представитель, порог 13 лет.
8. **Политика конфиденциальности** описывает только то, что реально делается; отдельная политика по данным о здоровье
   (WA); удаление аккаунта из приложения и по ссылке (Google Play); дисклеймер «не медицинское устройство».
9. **Вход:** Supabase Auth по email (magic link) — без Google OAuth, иначе обязателен Sign in with Apple.

**AI-коуч и внешние LLM.** Отправка данных о здоровье внешнему провайдеру LLM — обработчик, третье лицо и, вероятно,
трансграничная передача (GDPR ст. 28, гл. V; закон РК), а также внешний запрос, который правила проекта сейчас
запрещают; по Apple 5.1.2(i) — только с явного разрешения. Поэтому AI-коуч — **отдельный ADR и отдельное согласие**;
этот ADR внешнюю передачу не разрешает.

**Хранение и шифрование.** TLS везде; шифрование диска и бэкапов БД (копии шифруются до отправки в бакет ключом
региона — `infra/supabase/backup.sh`, #265); Row Level Security — пользователь видит только
свои строки; доступ сотрудников — через аудитируемую роль с MFA и журналом (это же закрывает «удалённый доступ из
РК» по EDPB). Полевое шифрование ключом сервиса (KMS) — для **свободного текста** (заметки чек-ина, заметки задач и
событий), а не для числовых полей здоровья: иначе SQL-аналитика, ради которой выбран A, стала бы невозможна.
Аналитика и модели читают не «сырые» таблицы, а **псевдонимизированные витрины** (без `user_id`, агрегаты не меньше чем
по N пользователям), которые собирает сервисная роль и только для пользователей с согласием (б). Псевдонимизированные
данные по GDPR остаются персональными (Recital 26) — облегчённого режима это не даёт. Сквозное шифрование «только у
пользователя» не выбрано (исключает серверного AI-коуча); можно вернуться к нему как к опции «приватный режим».

**Удаление.** «Удалить аккаунт» стирает данные на сервере в течение 30 дней (включая бэкапы по их циклу); локальные
данные остаются на устройстве, пока пользователь их не сотрёт.

### Открытые вопросы для разовой консультации

1. Ст. 12 закона № 94-V: распространяется ли на иностранное приложение без присутствия в РК; допустима ли схема
   «основная копия в РК + реплика в ЕС» (у Supabase нет региона в РК); применимость к данным, которые не покидают
   устройство, и к закрытому тесту «для личных нужд».
2. Реестр операторов персональных данных РК (ст. 27-1 пп. 2-4, с 25.08.2026): нужна ли регистрация.
3. Уведомление субъектов об утечке через eGov требует ФИО, ИИН и телефон, которых приложение не собирает.
4. Статус данных самотрекинга в РК («ограниченного доступа» или нет), актуальная редакция ст. 273 Кодекса о здоровье.
5. Структура контролёра: юрлицо в РК или в ЕС — последствия для доступа команды, SCC для подрядчиков из РК, запросы
   госорганов РК.
6. Момент, когда обработка становится «large scale» по GDPR (DPIA, DPO), и применимость исключения ст. 27(2) на тесте.
7. Являются ли сон, еда, тренировки, чек-ины и тест внимания «consumer health data» (WA, NV, CT) и «medical
   information» (CMIA § 56.06) — от этого зависит поток согласий и применимость CMIA без порогов.
8. С какого момента LifeOS — «vendor of PHR» по правилу FTC и считается ли инцидент у процессора нашим breach.
9. Правовая основа аналитики и моделей на псевдонимизированных данных; последствия отзыва согласия для обученных
   моделей; соответствие определению «deidentified data» (WA).
10. Статус Supabase и AI-вендоров как «third party» по Apple PLA и Health Connect Limited Use.
11. Условия внешней оплаты в США после решения Верховного суда (2027) и комиссии ЕС.

Источники разбора (первоисточники с цитатами) — в комментариях к issue #132.

## Последствия

- ✅ Данные остаются на устройстве и работают офлайн; облако добавляется, ничего не ломая.
- ✅ Открытый Postgres: аналитика и модели — SQL по витринам, без выгрузок из чужого формата.
- ✅ Хранение в разных странах — разные развёртывания одного стека.
- ⚠️ Протокол синхронизации — наш код: нужен контракт ядра и сильные тесты (раздел «Синхронизация», п. 10).
- ⚠️ Tombstone и детерминированные `id` меняют запись и чтение во всех модулях — отдельные issues по модулям после
  контракта ядра.

- ❗ До первой отправки данных реальных пользователей: разовая консультация по списку открытых вопросов, представитель

- ❗ Никаких сторонних аналитических SDK с доступом к событиям о здоровье: каждая такая передача — breach по правилу FTC.
- ⚠️ Self-hosted Supabase в РК — своя эксплуатация: обновления, мониторинг, восстановление из копии. Инфраструктура

## Решения владельца (2026-11-04)

1. **Рынки:** закрытые тесты в Казахстане, публичный запуск общемировой (ЕС, США и другие).
2. **Хостинг** (уточнено 2026-11-05): облако с первого дня, включая Казахстан; самый дешёвый вариант с базой на

   Supabase Free в ЕС — только staging без данных пользователей.
3. **Freemium:** одна облачная копия бесплатно, синхронизация между устройствами по подписке; остальное по таблице выше.

   правила сторов), записанный в этот ADR с указанием уверенности и открытых вопросов; **разовая консультация**
   специалиста по защите данных — перед первой отправкой данных о здоровье реальных пользователей за пределы теста.
   AI-коуч и внешние LLM — отдельным ADR.
5. **Облако с первого дня** и для закрытого теста в РК; требование ст. 12 выполняется размещением базы в РК
   (решение владельца от 2026-11-05 вместо предложенного «тест без облака»).
6. **Возраст облачного аккаунта:** 16+ (РК — 18+ или согласие законного представителя), младше — local-first без
   аккаунта (подтверждено владельцем 2026-11-05).
7. **Ячейки по регионам** (решение владельца от 2026-11-05, issue #172): архитектура ячеек с первого дня, хотя регион

   аккаунта и меняется только явной миграцией. Каждый регион — отдельное развёртывание со своими Postgres и Auth, без
   репликации и общих таблиц с данными пользователей; общие только код и схема. Бэкапы региона — в его юрисдикции.

   `infra/supabase/`, второй регион поднимается переменными среды (проверяется в CI).
