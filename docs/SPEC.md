# LifeOS — спецификация блока «Продуктивность»

Версия 0.3 · 2026-11-04 · владелец продукта: Petram · решения — [product-decisions.md](product-decisions.md)

**Что изменилось в 0.3.** Владелец отказался от сознательно суженного MVP: все десять блоков из исходной идеи
строятся, а веб-версия (PWA) — первый этап платформы, а не её финальная форма. Раздел 2 заменяет
«честные границы» на этапы платформы, раздел 3 перечисляет все блоки, раздел 4 задаёт вехи M5–M8,
раздел 5 расширяет контракт целей дня до версии 2. Версия 0.2 остаётся в истории git.

## 1. Зачем это приложение

Супер-приложение, которое со временем покрывает все этапы жизни. Первый блок — продуктивность.
Главное преимущество — **общие данные между блоками**: сон, еда, тренировки, задачи, время, медитации и
результаты тестов внимания лежат в одной базе, поэтому приложение перестраивает режим целиком,
а не по одному трекеру за раз.

Уникальная функция — **слой адаптации**: пользователь отмечает важное событие (экзамен, дедлайн,
собеседование), и все блоки заранее перестраивают нагрузку, сон, питание, тренировки, медитации,
ментальные тренировки и восстановление.

**Позиционирование:** «LifeOS готовит тебя к важному событию: сам перестраивает задачи, сон, тренировки,
питание и фокус». Два отличия от конкурентов: **план от события** (планирование назад от экзамена или
дедлайна, а не реакция на сегодняшнее состояние, как у Oura/Whoop) и **действие, а не совет** (приложение
меняет все блоки сразу, а не показывает корреляции, как Bearable).

**Принцип расширения.** Блок — это комплекс функций, соответствующий одному приложению-ориентиру.
Каждый новый блок обязан **читать цели дня** (`DailyTargets`) и **поставлять данные** правилам адаптации.
Блок, который только хранит записи, не даёт преимущества общей базы и в продукт не берётся.

**Первая аудитория:** люди в саморазвитии, которые уже трекают сон, еду, тренировки и привычки.

**Главное ограничение интерфейса:** обязательный ввод данных — **не больше 3 минут в день**, одним утренним
потоком (сон → чек-ин → тест внимания). Остальное — по желанию или автоматически из датчиков и
Health Connect / HealthKit (этап «Натив»).

## 2. Платформа и этапы

Один код на все платформы ([ADR-0008](adr/0008-web-and-native-one-codebase.md)): React-приложение
собирается и как PWA для браузера, и как нативное приложение для iOS и Android через Capacitor.
Данные хранятся **local-first** в IndexedDB (Dexie) на всех платформах; облако добавляет синхронизацию
и аналитику, но не заменяет локальную базу ([ADR-0001](adr/0001-local-first-pwa.md) в части модели данных).

| Этап              | Веха  | Что открывает                                                                                                                                            |
| ----------------- | ----- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Веб (PWA)**     | M1–M6 | Все блоки, которые работают без фоновых датчиков: задачи, привычки, время, питание, тренировки, сон вручную, медитации, тренажёры ума, заметки, прогресс |
| **Натив**         | M7    | Будильник с умным окном подъёма, трекинг сна по акселерометру и микрофону, уведомления, импорт из Health Connect / HealthKit                             |
| **Облако и SaaS** | M8    | Аккаунты, облачная копия, синхронизация между устройствами, аналитика, граница freemium, затем AI-коуч и модели на данных всех пользователей             |

Функция, которая на текущем этапе невозможна технически, **не вычёркивается**: она получает веху
и issue, а в веб-версии показывается объяснение «доступно в приложении для телефона».

- **Язык интерфейса**: русский. Код, имена и комментарии — английский.
- **Своя реализация**: код других приложений не копируем, берём только идеи функций.
- **Защита данных**: экспорт/импорт JSON сейчас, облачная копия — на этапе M8. Данные о здоровье не покидают
  устройство до ADR о бэкенде и согласии пользователя.

## 4. Приоритеты и вехи

Метки приоритета: **P0** — делается в первую очередь; **P1** — следующая очередь, агенты берут после P0;
**P2** — нужно решение владельца, аккаунт или контент (хостинг, сторы, аудио), агенты берут только по команде.
P2 не означает «не делаем».

**Завершить MVP (M3 Адаптация, M4 Релиз MVP)** — без изменений относительно 0.2: онбординг, сквозной сценарий
«экзамен перестраивает режим», PWA-иконки, импорт истории.

**M5 Курс 0.3 — контракты.** Всё, что нужно новым дорожкам до старта:

1. Этот документ, ADR-0008, решения владельца, бэклог полной картины.
2. **Цели дня v2** (раздел 5.3): питание, тренировки, медитация, ум, будильник, привычки.
3. **Каркасы блоков** `nutrition`, `training`, `meditation`, `progress`, `notes` и их таблицы; общий путь записи тренировки.
4. **Навигация для 12 блоков**: хаб «Сегодня», закреплённые вкладки, экран «Все блоки».
5. Перенос дневника еды в `nutrition` и журнала тренировок в `training`; `health` остаётся блоком сна.

**M6 Новые блоки.** Дорожки идут параллельно, каждая начинается с чтения целей дня:

- `nutrition`: журнал веса и тренд → адаптивный расход энергии и цели КБЖУ → цели по фазам в дневнике.
- `training`: программы и шаблоны → выполнение плана пишет журнал → периодизация к событию.
- `meditation`: таймер и дыхание → библиотека сессий и план по фазам → аудио (P2, контент).
- `cognition`: n-back → Струп и Шульте → план из целей дня.
- `progress`: опыт и уровни → навыки и квесты.
- `notes`: страницы со ссылками → поиск, обратные ссылки, шаблон подготовки.
- `habits`: режим «только ключевые». `today`: правило по тесту внимания.
- `infra`: сквозной сценарий «экзамен перестраивает все блоки».

**M7 Натив.** Оболочка Capacitor и сборка Android в CI → уведомления → будильник с окном подъёма →
трекинг сна по датчикам → импорт из Health Connect / HealthKit. iOS-сборка после аккаунта Apple (P2).

**M8 Облако и SaaS.** ADR о бэкенде, синхронизации и праве на данные о здоровье (P1, черновик пишет агент) →
аккаунт и облачная копия → синхронизация → граница freemium и флаги функций → аналитика (P2: нужны хостинг
и решения владельца). Затем AI-коуч и персонализация с эластичными границами (см. product-decisions.md).

## 5. Слой адаптации (ядро продукта)

### 5.1 Важное событие (`LifeEvent`)

Поля: название, тип (`exam`, `deadline`, `interview`, `competition`, `travel`, `other`), дата и время,
важность 1–3, связанный проект задач (опционально), сколько дней готовиться (по умолчанию 7).

### 5.2 Фазы

| Фаза       | Когда         | Смысл                                                              |
| ---------- | ------------- | ------------------------------------------------------------------ |
| `prep`     | от T−N до T−2 | подготовка: больше фокуса на связанном проекте, режим сна стабилен |
| `taper`    | T−1           | разгрузка: лёгкий день, ранний отбой, разгрузочная тренировка      |
| `event`    | день T        | день события                                                       |
| `recovery` | T+1           | восстановление                                                     |
| `normal`   | всё остальное | обычный режим                                                      |

### 5.3 Цели дня (`DailyTargets`) — общий контракт для всех блоков

Один чистый движок `computeDailyTargets(date, context)` возвращает цели на день. Каждый модуль
**читает** их и показывает у себя; ни один модуль не придумывает свои правила адаптации.

| Блок       | Поля v1 (есть)                                               | Поля v2 (контракт M5)                                                       |
| ---------- | ------------------------------------------------------------ | --------------------------------------------------------------------------- |
| задачи     | `taskCapacityMin`, `focusProjectId`, `allowDeferLowPriority` | —                                                                           |
| привычки   | —                                                            | `habitsMode`: `all` / `essential`                                           |
| фокус      | `focusPomodoros`                                             | —                                                                           |
| сон        | `sleepHours`, `bedtime`                                      | `wakeTime`, `wakeWindowMin` (окно умного будильника)                        |
| тренировки | `maxWorkoutIntensity`                                        | `deload` (разгрузочный день по плану)                                       |
| питание    | `caffeineCutoff`, `noNewFoods`                               | `kcal`, `proteinG`, `fatG`, `carbsG` (пусто, пока нет данных о весе и цели) |
| медитация  | `meditationMin`                                              | `meditationKind`: `breathing` / `focus` / `sleep` / `body`                  |
| ум         | —                                                            | `mindTrainingMin`                                                           |
| все        | `phase`, `activeEventId`, `reasons[]`                        | —                                                                           |

`reasons[]` — человекочитаемые причины каждой подстройки («Экзамен через 3 дня: +2 фокус-сессии»).

### 5.4 Правила (декларативные, расширяемые)

Правила хранятся как данные (`AdaptationRule[]`), а не как `if` в UI. Есть:

1. Фаза события меняет цели (таблица в `src/core/adaptation/rules.ts`).
2. Сон прошлой ночи < 6 ч → ёмкость дня −20%, интенсивность тренировки не выше `light`.
3. Энергия в чек-ине ≤ 2 → ёмкость дня −20%.
4. Несколько событий сразу → берётся событие с наибольшей важностью, при равенстве — ближайшее;
   два и более событий от сегодня до T+3 → ёмкость −10%.
5. Три ночи подряд < 6,5 ч (все три ночи записаны) → отбой на 30 минут раньше.
6. Вчера тренировка с RPE ≥ 8 → сегодня не выше `moderate`.

Контракт v2 (#104):

7. `taper` и `event` → `kcal` не ниже поддерживающего расхода (дефицит снимается), `deload = true`, `mindTrainingMin` ≤ 5.
8. `event` → `habitsMode = essential`, `meditationKind = breathing`; `recovery` → `meditationKind = body`.
9. Низкая энергия → `mindTrainingMin = 0`.
10. Питание: `kcal`, `proteinG`, `fatG`, `carbsG` считаются, только когда известны расход (`nutrition.expenditure`),
    цель (`nutrition.goal`) и вес. Изменение веса `ratePct` % в неделю ≈ 7700 ккал/кг; дефицит не больше 25% расхода;
    белок 1,8 г/кг (1,6 — при поддержании), жиры 0,8 г/кг, углеводы — остаток.

Планируется:

11. Медиана PVT хуже личной нормы на 20% → отсечка кофеина раньше, ёмкость −10% (дорожка `today`).

Важно: это рекомендации режима дня, а не медицинские советы. В интерфейсе цели показываются
как предложения, их можно переопределить.

### 5.5 Сигналы для правил

Контекст движка собирает `loadDailyTargets` из таблиц всех блоков: сон, чек-ин, тренировки вчера,
события, базовый режим; с контрактом v2 (#104) — расход и цель питания, последний вес, медианы PVT за 14 дней,
минуты медитации вчера (`loadAdaptationContext` в `src/core/adaptation/useDailyTargets.ts`).
Персонализация с эластичными границами (байесовское обновление норм) — отдельный ADR и прототип (issue #44).

### 5.6 Модель данных новых блоков

Таблицы и типы появляются контрактной issue «каркасы блоков» (M5). Все записи наследуют `BaseRecord`
(`id`, `createdAt`, `updatedAt`); даты дней — `DateKey`. Индексы — в скобках.

| Таблица              | Владелец   | Поля                                                                                                                                        |
| -------------------- | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `weightLogs`         | nutrition  | `date` (уникальный), `kg`                                                                                                                   |
| `programs`           | training   | `name`, `archived`, `days: { weekday, exercises: { name, sets, reps?, weightKg?, rpeTarget? }[] }[]`, `weeks` (длина плана, по умолчанию 4) |
| `plannedSessions`    | training   | `programId`, `date` (`[programId+date]`), `exercises` (копия на день), `status: planned \| done \| skipped`, `workoutLogId?`                |
| `meditationSessions` | meditation | `date`, `startedAt`, `durationMin`, `kind: breathing \| focus \| sleep \| body`, `pattern?` (`4-7-8`, `box`), `completed`                   |
| `mindSessions`       | cognition  | `date`, `kind: nback \| stroop \| schulte`, `durationMs`, `accuracyPct`, `level?` (n для n-back), `meanRtMs?`, `errors?`                    |
| `notes`              | notes      | `title`, `body` (markdown), `linkIds` (мульти-индекс: id проекта, события или `DateKey` дня), `pinned?`                                     |
| `xpEvents`           | progress   | `date`, `source` (`quest`), `questId`, `amount`                                                                                             |

Настройки блоков — ключи `settings`: `nutrition.goal` (`kind: lose \| maintain \| gain`, `ratePct`),
`nutrition.expenditure` (`kcal`, `updatedAt`), `nutrition.profile` (`heightCm`, `birthYear`, `sex`).
Привычки получают поле `Habit.essential?: boolean` (контракт «цели дня v2»).

## 6. Критерии готовности

**MVP (M4):**

- Все P0-функции вех M1–M4 работают офлайн после первой загрузки.
- `npm run check` и `npm run e2e` проходят без ошибок.
- Движок адаптации покрыт тестами для каждой фазы и каждого правила.
- Парсер быстрого ввода покрыт тестами (не меньше 20 примеров на русском).
- Экспорт → очистка → импорт восстанавливает все данные (тест).
- Интерфейс удобен на экране телефона шириной 360 px.

**Полная картина 1.0 (M6–M8):**

- Каждый блок из раздела 3 читает хотя бы одно поле `DailyTargets` и поставляет хотя бы один сигнал в контекст движка.
- Сквозной сценарий «экзамен перестраивает все блоки» зелёный.
- Нативная сборка Android собирается в CI; будильник, датчики сна и импорт здоровья работают на устройстве.
- Облачная копия и синхронизация покрыты тестами; согласие на обработку данных о здоровье получено до их отправки.
